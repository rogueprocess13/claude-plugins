# Ticket Audit Exec

Two-phase apply agent for recommendation checklists generated by `/ticket-audit`. Reads `{AUDIT_DIR}/recommendations/*.md`, applies findings in two separate invocations, archives completed files.

**Phases:**
- **Run 1 — Needs-info**: Delegates each pending needs-info item to `/ticket-critique {ID}`, then exits. Human resolves flagged tickets before run 2.
- **Run 2 — Structural**: Posts comments on affected tickets for pending structural + drift items, then archives.

**Flags:**
- `--file <path>` — target a specific recommendation file
- `--dry-run` — print planned actions without mutations or file changes

**Key invariants:**
- Never mutates Linear directly — needs-info goes through ticket-critique; structural posts comments only
- Hard exit after run 1 — structural phase cannot run in the same invocation
- Write-ahead `[>]` for crash recovery — prevents double-apply on resume
- Dedup guard (`audit-comment-guard.sh`) before every delegation/post

---

## Steps 0–2: Resolve and parse the checklist

Pass the flags through (`--file <path>` skips the selection sort; `--dry-run` is the fast path):

```bash
bash ~/.claude/skills/lib/ticket-audit-exec.sh run {FLAGS}
```

It prints `DRY_RUN`, `AUDIT_DIR`, `TARGET_FILE` (the given file, else the most recent recommendation file), `PHASE`, `SOURCE_ID`, `PENDING_NEEDS_INFO`, `PENDING_STRUCTURAL`, then one `ITEM=<needs-info|structural>|<state>|<ticket_id>|<detail>|<detail_clean>|<all_ticket_ids>` line per pending or resumed item. Exit 1: no file resolved — show the error and stop. Each later call below is the same script (`lib/ticket-audit-exec.sh` header), so no step relies on functions sourced in an earlier shell.

---

## Step 3: Dry-run fast path

If `--dry-run` is set, print planned actions and exit without mutations.

**If DRY_RUN is true:**

Read the phase from Step 2's output. For each section:

1. Print the resolved file path, current Phase, and source ID.
2. For each pending needs-info item (`state` = `pending` or `resumed`): print ticket ID, detail, and "→ delegate to /ticket-critique {ID}"
3. For each pending structural item: print ticket ID, detail, and "→ post comment to {ID}"
4. If `needs-info` phase with 0 pending → print "→ would fast-path to Phase: needs-info-done"
5. If `needs-info-done` phase with 0 pending structural → print "→ would proceed directly to archive"
6. If `structural-done` phase → print "→ would archive file"
7. End with "=== END DRY RUN (no mutations performed) ===" and exit 0.

**Do not make any Linear API calls. Do not modify any files.**

---

## Step 4: Needs-info phase (run 1)

### 4a: Phase skip

If PHASE is `needs-info-done` or `structural-done`:
- Print "Needs-info phase already complete (Phase: {PHASE})"
- Skip to Step 5.

### 4b: Empty section fast-path

If PENDING_NEEDS_INFO is 0:
```bash
bash ~/.claude/skills/lib/ticket-audit-exec.sh advance "{TARGET_FILE}" needs-info-done
```
Print run 1 summary (0 delegated, 0 failed) and exit 0.

### 4c: Process each needs-info item

For each `ITEM=needs-info|…` line (state `pending` or `resumed`):

1. **Write-ahead and dedup guard** (marks the item `[>]`, then checks for an existing `Source: {SOURCE_ID}:{TICKET_ID}:needs-info` comment):
   ```bash
   bash ~/.claude/skills/lib/ticket-audit-exec.sh start "{TARGET_FILE}" {TICKET_ID} "{SOURCE_ID}" needs-info
   ```
   `DEDUP` → already handled (the item is marked done); go to the next item. `PROCEED` → continue.

2. **Delegate to ticket-critique**, passing the audit finding (`detail_clean`) as context:
   ```
   /ticket-critique {TICKET_ID} --from-audit \
     --source-marker "{SOURCE_ID}:{TICKET_ID}:needs-info"
   ```

3. **Record the result:** `bash ~/.claude/skills/lib/ticket-audit-exec.sh done "{TARGET_FILE}" {TICKET_ID}` on success (count it as delegated), `bash ~/.claude/skills/lib/ticket-audit-exec.sh failed "{TARGET_FILE}" {TICKET_ID}` on failure (record "{TICKET_ID}: ticket-critique failed").

   **Dedup coverage:** ticket-critique with `--from-audit` includes `Source: {source-marker}` in its comment footer. On crash/resume, the guard finds this marker and skips re-delegation.

### 4d: Advance phase and print summary

After all needs-info items processed:

```bash
bash ~/.claude/skills/lib/ticket-audit-exec.sh advance "{TARGET_FILE}" needs-info-done
```

Print run 1 summary:
- Items delegated: (count)
- Failed: (count) with list of `[!]` ticket IDs
- Instruction: "Resolve needs-info tickets, then re-run ticket-audit-exec for structural phase."

Exit 0. **Do not proceed to Step 5 in the same invocation.**

---

## Step 5: Structural phase (run 2)

This step only executes if PHASE is `needs-info-done` (Step 4 was skipped due to phase gate in 4a).

### 5a: Phase gate

If PHASE is `needs-info` (run 1 not complete):
- Print "Needs-info phase not yet complete. Resolve flagged tickets and re-run ticket-audit-exec."
- Exit 0.

### 5b: Empty section fast-path

If PENDING_STRUCTURAL is 0:
- Print "No pending structural items — proceeding to archive."
- Skip to Step 6.

### 5c: Process each structural item

For each `ITEM=structural|…` line, run 4c step 1 with kind `structural` (`bash ~/.claude/skills/lib/ticket-audit-exec.sh start "{TARGET_FILE}" {TICKET_ID} "{SOURCE_ID}" structural`), then:

3. **Compose and post comment**: Extract the finding type from the detail (first colon-delimited segment, e.g., "merge candidate", "split candidate", "duplicate", "drift", "goal misalignment"). Use `detail_clean` (stripped of the finding type prefix) to avoid redundancy.

   **Multi-ticket findings** (merge candidates, duplicates): When `all_ticket_ids` contains more than one ticket ID, post the comment on EVERY affected ticket. For example, if `all_ticket_ids` is "WIL-78 WIL-79", post on both WIL-78 AND WIL-79.

   Compose the comment body:
   ```
   Audit recommendation: {finding_type}
   {detail_clean — the finding description without the redundant type prefix}
   Source: {SOURCE_ID}:{TICKET_ID}:structural
   ```

   Post via the MCP Linear comment tool. Post on the primary ticket AND on each sibling ticket from `all_ticket_ids`. Guard each sibling separately: `bash ~/.claude/skills/lib/audit-comment-guard.sh {SIBLING} "{SOURCE_ID}:{TICKET_ID}:structural"` (exit 0 = already posted, skip it).

   On success (all posts): `bash ~/.claude/skills/lib/ticket-audit-exec.sh done "{TARGET_FILE}" {TICKET_ID}`, and add the number of tickets commented on to the comment count. On failure (any post fails): `bash ~/.claude/skills/lib/ticket-audit-exec.sh failed "{TARGET_FILE}" {TICKET_ID}`, and record "{TICKET_ID}: comment post failed on {sibling} — {error}" in the failure list.

### 5d: Advance phase to structural-done

After all structural items processed:

```bash
bash ~/.claude/skills/lib/ticket-audit-exec.sh advance "{TARGET_FILE}" structural-done
```

---

## Step 6: Archive

After structural phase completes, or if both phases were already done:

```bash
bash ~/.claude/skills/lib/ticket-audit-exec.sh archive "{TARGET_FILE}"
```

It archives only when no item is pending (`ARCHIVE_PATH=`), else prints `PENDING — skipping archive`, and reports a file already in `{AUDIT_DIR}/archive/`.

---

## Step 7: Print summary

Run 1 prints its summary in Step 4d.

### Run 2 summary (after Step 5+6)

Print:
- Comments posted: (count)
- Failed: (count) with list of `[!]` ticket IDs and error reasons
- Archive path (if archived)
- If any `[!]` items remain: "Investigate failed items manually — see checklist for details."

---

## Item state reference

| State | Markdown | Meaning | Action on re-invocation |
|---|---|---|---|
| Pending | `- [ ]` | Never attempted | Process normally |
| In-progress | `- [>]` | Prior run crashed during processing | Re-process from start (dedup guard prevents double-apply) |
| Complete | `- [x]` | Applied successfully | Skip |
| Failed | `- [!]` | Error during application | Skip (reported in summary; human investigates) |
