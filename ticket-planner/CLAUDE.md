# CLAUDE.md — ticket-planner

Plugin-level guidance for Claude Code when working inside this plugin directory. See also: [repo-level CLAUDE.md](../CLAUDE.md) for marketplace-wide conventions.

## Plugin purpose

Autonomous 11-phase planner that turns business ideas into dependency-ordered planned tickets the existing `ticket-auto` pipeline consumes without special-casing. Sits upstream of `ticket-auto` and `fleet-controller` — plans, then hands off.

Produces against frozen consumption-side contracts: the Planner Context block schema (its `Pre-approved` field, never a label — tracker-planner-and-fallback-cutover retired the labels this line used to name), artifact plane, and feedback aggregation. Does not re-specify them.

## 11-phase state machine

```
Appraisal → Discovery → Architecture → Specify → Review → Consensus →
Crosscheck → EpicGen → TicketGen → Refinement → Completed
```

Each phase runs as an isolated agent — except Crosscheck and Refinement, which are deterministic bash (see below; Refinement additionally spawns two `dor-semantic-agent` instances per ticket that needs a semantic pass, but the phase's own decisions — which tickets need one, whether to halt, whether to stamp the epic — are bash). State lives in a durable append-only log under `${REPOS_ROOT}/.ticket-auto/initiatives/{ID}/`. The router reads the log to derive position — no state held in memory. Resume re-derives position by re-reading the log.

Crosscheck sits between Consensus and EpicGen: the last artifact-only phase, and the phase that gates the first Linear write (`PLANNER_DRY_RUN_PHASE` / `PLANNER_CREATE_GATE_PHASE` — see `planner-router.sh`). It wires in the citation ([#172](https://github.com/willard-pro/claude-plugins/issues/172)), propagation ([#173](https://github.com/willard-pro/claude-plugins/issues/173)), and bypass-sweep/discovery-gap ([#174](https://github.com/willard-pro/claude-plugins/issues/174)) checks, writing every finding to state.log as `META|crosscheck|fail|<CODE> <message>` (or `warn|info` for non-blocking codes) and halting the dispatch loop on a blocking one ([#178](https://github.com/willard-pro/claude-plugins/issues/178)). A blocking finding that is genuine but expected (a documented rescope, not a checker bug) can be overridden with `resume <ID> --accept CODE:"reason"`, which persists `META|crosscheck|accepted|<CODE> <reason>` and makes that code non-blocking on the next run ([#222](https://github.com/willard-pro/claude-plugins/issues/222)).

## Key design decisions

- **Stateless-router pattern**, copied deliberately from `ticket-auto`. State lives in a durable log; the router reads it to determine position; each phase runs as an isolated agent with no inline reasoning between phases.
- **Phase transitions recorded before side effects.** Every entity-creating phase first records intent, then checks whether the entity already exists before creating it, keyed by a deterministic identifier. Safe to re-enter any phase.
- **Generate against the validator.** `planned-ticket-check.sh` is invoked on generated tickets before creation. A ticket that fails validation is not created. Since [#285](https://github.com/willard-pro/claude-plugins/issues/285), `planner_validate_ticket` also calls ticket-auto-pipeline's `planned-ticket-body-check.sh` (`check_planned_body`) when given a `ticket_type` — the same required-`##`-sections check ticket-auto's gate-check (Check 2.7c) runs, but at ticket-creation time instead of at the approve gate several phases later.
- **Confidence per ticket from concrete signals.** Derived from services identified, symbols resolved, prior art found — never a uniform constant.
- **Dependencies as the ticket manifest's `blocked_by` field, validated acyclic.** Cycle detection before any ticket is created. (Historically these were `blocked-by:{ID}` labels, retired with the rest of the planner's labels.)
- **Auto-dispatch wired at the detector, approval gate untouched.** Dispatches without human command; still stops every ticket at the human approval gate.
- **The safe state is the default; creating is the deliberate act.** `plan` ends at Crosscheck and writes nothing to Linear — a constant in the phase sequence, not a flag that could fail to take effect. Crossing the write boundary takes a separate `resume <ID> --create`, which persists `META|create-authorized|done` before the loop starts. Three disk-backed guards enforce it: the stop check, `planner_create_gate_check` before dispatch, and a re-check inside the Epic Gen and Ticket Gen agents.
- **Crosscheck is the one phase that is not an agent.** Every other phase in `planner_phase_sequence` is dispatched by spawning a Claude agent with a prompt from `planner_prompt_for_phase`. Crosscheck has no prompt — SKILL.md's dispatch loop special-cases it (step 1a) and calls `planner_crosscheck_run` as plain bash instead. A blocking finding is treated as an immediate stop, not a retry: the check is deterministic, so re-running it against unedited artifacts cannot produce a different result. Only editing the artifacts and issuing `resume` can.
- **The terminal phase is dispatched, not assumed.** `planner_position_derive` returning `Completed` means phase 11 still has to run — only the empty string means the initiative is finished. The dispatch loop runs it in the same invocation as Refinement's own gate passing clean or legacy-skipping (it writes only to disk, so no gate stands between them) and `planner_completion_verify` refuses to report the run complete without `artifacts/COMPLETED.md` and the terminal log entry. Two live initiatives shipped tickets to Linear — the part operators watch — with no completion summary before this was enforced ([#226](https://github.com/willard-pro/claude-plugins/issues/226)).
- **An absent `--project` is a question, not a default.** Epic Gen's project gate (`planner-project-gate.sh`) runs before the first Linear write when neither `--project` nor `--no-project` was configured. One project on the team whose name matches the initiative stops the phase for the operator to confirm or opt out; zero or several proceed as before but record `EpicGen|project|skip`. It never picks one — the same discipline `planner_linear_resolve_team_id` applies to team ambiguity, extended to the field whose silent omission put 4 epics and 24 tickets in Linear with `project: null` ([#256](https://github.com/willard-pro/claude-plugins/issues/256)).
- **Invocation config crosses the loop on disk, never in the environment.** The dispatch loop spans one process per phase with an Agent tool call between, so `export` does not reach the next iteration. Flags are parsed once and written to the state log; every consumer reads them back with `planner_config_get`. This is the same rule that governs position and retry counts, and the same defect class as #138 and #144.
- **Regenerate is an explicit flag.** Feedback ingested only when `Regenerate` label is present. Undispatched Backlog tickets only — in-flight work untouched.
- **The installed copy is refreshed from the source checkout, not only from the marketplace.** `hooks/planner-lib-sync.sh` runs on `SessionStart`. It always does what the old one-line hook did — copy the installed cache's `lib/*.sh` into `~/.claude/skills/lib/` — and then, when it can detect a source checkout, overlays that checkout's working-tree `lib/*.sh` onto *both* the cache and the skills lib ([#234](https://github.com/willard-pro/claude-plugins/issues/234)). Writing the cache is the load-bearing half: `planner_resolve_lib_root` prefers the cache over the skills lib, so a skills-lib-only sync would never be the copy that runs. Detection precedence: `PLANNER_DEV_ROOT` → `CLAUDE_PROJECT_DIR` walked upwards → the checkout recorded by an earlier session. Only a repository's *main* worktree is ever recorded, so a throwaway issue-branch worktree feeds the session started inside it and nothing else. A checkout older than the installed version is refused rather than allowed to downgrade it, and `PLANNER_DEV_SYNC=0` turns the overlay off. Scope is `lib/*.sh` — the file set the hook already owned; skill markdown and the hook script itself still arrive by marketplace install.
- **`planned-entry-gate` stays dormant by decision.** Specified but deliberately unimplemented. Confidence ≥ 0.85 + the Planner Context block's `Pre-approved: true` field would bypass human approval gate. Revisit only after: ≥ 10 completed initiatives with real feedback data, drift consistently ≤ 0.10 at confidence ≥ 0.85, zero incidents from auto-approved tickets, and explicit operator opt-in. See `docs/ticket-planner.md#planned-entry-gate-dormancy`.
- **Tickets arrive ready by construction, not just checked afterward (planner-ready-by-construction).** TicketGen's Body section contract requires a `## Verification Plan` table (`### Per-Criterion Verification`, one row per Acceptance Criteria line, `✓`/`Y` marked only when a row states a genuinely concrete, checkable value) and `## Test Data Prerequisites` on every type, not bug-only. Specify feeds it: a `## Verification Notes` table keyed by each AC's verbatim text (role, test data, Source, expected value, verifiable), turned into the table by `planner_ticketgen_vplan` in bash — matched by criterion text, never by position, since a hand-amended numbered list stops following AC order ([#499](https://github.com/willard-pro/claude-plugins/issues/499)). Each test-data need also names its Source (#503, [docs/test-data-source.md](docs/test-data-source.md)) in the table's `Source` column, and Crosscheck blocks on data no spec owns. This closes the gap the Refinement phase's deterministic check (`VPLAN_MISSING`/`VPLAN_ROW_GAP`/`VPLAN_UNVERIFIABLE`) otherwise reports advisory on every planned ticket, since nothing previously generated the table at all. `ticket-auto-pipeline/lib/dor-check.sh`'s new `DOR_STRICT_VPLAN` (default `false`) lets a host promote those three codes to hard once it trusts the planner's table quality — no host enables it by default.
- **Business framing is additive, never a rewrite of the contract (planner-business-framing).** Specify writes `## Business Outcomes` (O-ids, sourced from intent.md → appraisal.md → `NEEDS_HUMAN_DECISION`, never invented) and classifies every spec `Kind: business | enabler` with `Serves`/`Enables` in its Signals JSON. Ticket bodies open with `## Summary` and `## Outcome` (or `## Enables`), keep the type template's why/outcome headings, and move all code-level detail into `## Technical Context`. Enablers stay technical — no fake user stories. Those template headings must stay: `dor-check.sh`'s hard `INTENT_MISSING` code matches them by exact name, and `test-planner-business-framing.sh`'s negative control fails if they are dropped. Deterministic business linting is a separate, later change.
- **Test data is derived and synthesized, never hand-authored as a pack (planner-test-data-derivation).** Discovery writes an epic-wide `## Test Data Inventory` (a sealed intent's `## Test Data` section, when it has real content, is pointed at as input — grill-test-data-dimension); Specify derives each Verification Notes row from the AC's Given/When and writes `Source: generate` for data nobody produces; Crosscheck flags specs with no notes (`VERIFICATION_NOTES_MISSING`) or with all-`none` rows whose criteria imply data (`TEST_DATA_IMPLIED`, answered by a hash-keyed `TESTDATA_CONFIRM` line in consensus.md), then its `testdata-synth` sub-step writes synth-marked chore TD specs plus a sidecar of Source overrides and `blocked_by` edges — consumer specs are never edited. ticket-auto's VERIFY runs a merged TD blocker's `Seed command:` (`seed-apply.sh`) before UAT. Contract: [docs/test-data-source.md §3](docs/test-data-source.md).

## Determinism boundary

- **Bash side (deterministic):** State log parsing, position derivation, phase transition validation, entity idempotency checks, dependency acyclicity validation, `planned-ticket-check.sh` and `planned-ticket-body-check.sh` invocation, confidence signal derivation, and the whole TicketGen ticket — creation order, dependency set, title, type, body, Verification Plan rows, Related Tickets, Planner Context (`planner-ticket-body.sh`, [#499](https://github.com/willard-pro/claude-plugins/issues/499)). The same spec set produces byte-identical bodies; the TicketGen agent runs one script and reports.
- **Agent side (LLM):** Per-phase reasoning — appraisal, discovery, architecture, proposal, review, consensus, spec writing (the spec's Description *is* the ticket body, humanized during Specify), epic body generation, re-planning decisions.

The router is bash; phases are Claude agents. The router never reasons about content — it only reads the log, validates transitions, and spawns the next phase.

## Headless / orchestrated use

A caller with no terminal (dexter's Slack bridge, a dashboard, a script) cannot read
halt prose, so it runs **describe → answers → resume**:

1. `bash lib/planner-stop-describe.sh <INIT_ID>` — a human-hold v2 block naming the
   stop and its questions, or `REASON=COMPLETED`/`RUNNING`/`FAILED_RETRY_EXHAUSTED`.
2. The caller gets the answers to a person and writes an answers file (`round`, plus
   `id`/`value`/`answered_by`/`role`/`ts` per answer — format in
   `ticket-auto-pipeline/docs/human-hold-schema.md` § Schema-Version 2).
3. `/ticket-planner resume <INIT_ID> --answers <file>` — `planner-answers.sh` turns each
   answer into the flag its binding names, then the resume runs as usual.

Bash decides everything — the stop reason, the binding-to-flag mapping, idempotency.
No agent reads an answer and decides what it means, and answer text never reaches a
shell unquoted. The halts are unchanged: same prose, same `exit 0`, guarded by the
halt goldens in `test-planner-stop-describe.sh`.

An open business decision stops the run before Review (planner-specify-waiting-on-human).
Specify writes `**Outcome:** NEEDS_HUMAN_DECISION — <question>` when no source states
an outcome; SKILL.md step 1c runs `planner_specify_gate` before dispatching Review and
halts on an open one. The describer reports it as `SPECIFY_DECISION` (`KIND input`,
`AUDIENCE either`, binding `specify-answer:O<n>`). An answer, a `__defer__`, or a hand
edit replaces the marker line in proposal.md, one line for one line — no `waiting`
status, no derivation change, no Specify re-run.

**A question back is not an answer.** When the person asks something instead of
answering ("why do you need this?"), the caller runs
`bash lib/planner-artifact-qa.sh <INIT_ID> --question-file <f> [--about <QID>]` and
posts the JSON `.answer`. It is a sandboxed, read-only Q&A over the artifacts; it never
answers, closes or renumbers the open round, so the pending question stays pending.
See the `planner-artifact-qa.sh` lib row above and SKILL.md § Headless use.

## State log format

Pipe-delimited, same convention as ticket-auto's pipeline log. Full spec: [state-log-format.md](state-log-format.md).

```
ISO|PHASE|STEP|STATUS|MSG
```

Statuses: `start`, `done`, `fail`, `skip`. Phases: Appraisal, Discovery, Architecture, Specify, Review, Consensus, Crosscheck, EpicGen, TicketGen, Completed. `META` pseudo-phase for metadata (`schema`, `title`, `initiative-id`, `idea`, `intent`, `replan`), for Crosscheck findings (`crosscheck` step, status `fail` for a blocking finding, `warn` for a non-blocking one, or `accepted` for an operator-accepted genuine-but-expected finding via `--accept` — see [#176](https://github.com/willard-pro/claude-plugins/issues/176)/[#222](https://github.com/willard-pro/claude-plugins/issues/222)), for answered headless question rounds (`human-hold`, `start`/`done` with `round=N sha=…`), for Specify business decisions (`specify-answer` step lines, which never carry the answer text, and the `specify-gate` warn tripwire), and for durable invocation config (`create-authorized`, `stop-after`, `linear-project`, `no-project`, `linear-milestone`, `linear-project-id`, `linear-milestone-id`, `branch-override`, `no-tests-rule`, `uat-policy`, `base-branch`, `merge-policy`, `sync-policy`), the base-branch decision (`base-branch-source`), Crosscheck's `testdata-synth` sub-step (`Crosscheck|testdata-synth|start/done`), and the artifact `contract` version (`META|contract|start|test-data-source-v1`). Schema version `1` — declared as first line.

## Known sharp edges

- **Cross-plugin validator dependency:** `planner-ticket-validate.sh` depends on `planned-ticket-check.sh` from `ticket-auto-pipeline`. It resolves via a three-level fallback (plugin cache → skills lib → relative path). If the validator is unavailable (exit 3), ticket creation halts. There is no bundled copy — the dependency is deliberate to avoid schema drift. When `planner_validate_ticket` is called with a `ticket_type` ([#285](https://github.com/willard-pro/claude-plugins/issues/285)), it additionally resolves `planned-ticket-body-check.sh` as a sibling of whichever `planned-ticket-check.sh` copy it found (same directory, so the same three-level fallback covers it) and runs `check_planned_body` against the composed description before creation — missing that file is the same exit-3 hard stop.
- **Cross-plugin branch directive dependency:** `branch-directive-gen.sh` resolves `branch-directive-check.sh` from `ticket-auto-pipeline` via the same three-level fallback (`_resolve_branch_directive_checker`). No bundled copy — a drifting duplicate would let generated blocks silently fail downstream validation. Generated blocks are round-trip tested through the canonical validator.
- **The phase prompts can reference helpers that are not in their own scope.** A prompt is a heredoc, not a script the linter sees: a call to a function no `source` line brings in fails at *agent* runtime, in a shell nothing in this repo executes. Epic Gen shipped exactly that — `_extract_md_section`/`_extract_field` (ticket-auto-pipeline's) called with no source line and the error swallowed by `2>/dev/null || true`, so the Branch Directive idempotency check silently read empty ([#228](https://github.com/willard-pro/claude-plugins/issues/228)). Every helper a prompt calls must be defined in a file that same prompt sources; a cross-plugin one needs a resolver, not an assumption. `test-branch-directive-gen.sh` (M4) guards this one call site — nothing guards the rest generically.
- **`planner-artifacts.sh` lives in ticket-auto-pipeline, not planner.** The artifact resolver that reads Planner Context blocks and resolves per-ticket artifact directories is in the downstream plugin. The planner writes artifacts; ticket-auto reads them. Don't look for this file in planner's `lib/`.
- **State log pipe character in message field:** `planner_state_write` replaces `|`, CR and LF in the message with spaces ([#499](https://github.com/willard-pro/claude-plugins/issues/499)) — a ticket title written into a `META|ticketgen|step` line could otherwise forge an `EpicGen|...|EPIC_ID=` line. Lines appended by anything other than `planner_state_write` are not covered, so readers of a specific line (`planner_epic_id`, `planner_refinement_legacy`) anchor on the phase and step fields (`^[^|]*\|EpicGen\|[^|]*\|done\|EPIC_ID=`) rather than substring-matching the whole line. `planner_state_repair` still preserves trailing fields for older logs.
- **Nothing may read a flag variable after argument parsing.** `PLANNER_UNTIL`, `PLANNER_REVIEW_HOLD`, `LINEAR_PROJECT`, `LINEAR_PROJECT_MILESTONE` `PLANNER_BASE_BRANCH`/`PLANNER_MERGE_POLICY`/`PLANNER_SYNC_POLICY` and the branch flags are read exactly once, in the shell that parses arguments, and persisted there. A `${LINEAR_PROJECT:-}` reintroduced into the router or a phase prompt reads empty in production and breaks nothing visibly — `test-planner-config-durability.sh` greps for it, and is the only thing that will notice.
- **Same-process tests cannot see the dispatch-loop boundary.** A suite that sets a variable and reads it back in the same shell will pass while the feature is entirely broken in production; that is exactly how #141 shipped with 25 passing tests. Anything that has to survive between phases belongs in `test-planner-config-durability.sh`, which runs each step in a separate `bash -c`.
- **Phase concurrency lock:** `planner_phase_lock` uses a PID-based lock file. If the lock holder crashes without cleanup, a stale lock blocks resume until manually removed or until the PID is no longer alive. `planner_state_init` auto-removes stale locks, but `planner_phase_lock` itself does not.
- **Prompt phase positions are derived, not hardcoded (planner-phase-count-derivation).** The 9 agent prompt functions (Crosscheck and Refinement have none — both are bash, not an agent; planner-refinement-phase) each set `local _pos _count` from `planner_phase_position <phase>` / `planner_phase_count` (`planner-state.sh`) before their `cat <<AGENT_PROMPT` and render `phase ${_pos} of ${_count}`. Both helpers derive from `planner_phase_sequence`, so inserting or removing a phase is a one-line edit to the sequence array — every prompt's rendered position and the total count follow automatically, with no per-function literal to update.
- **Prompt-embedded bash is escaped by hand, and it cuts both ways.** The 9 phase prompts are unquoted heredocs, so `${x}` interpolates the *generator's* `x` while `\${x}` emits a reference to the *agent's* `x`. Identical syntax, opposite meaning, and both directions fail silently:
  - **Under-escaped:** the expression runs at generation time and lands in the prompt as an empty assignment. This is how the TicketGen confidence block came to hand a bash-only decision back to the LLM.
  - **Over-escaped:** a variable that only exists in the generating function (`state_dir`, `initiative_id`, `safe_idea`, the config refs) reaches the agent's shell, where it is unset and expands to empty. `"\${state_dir}/state.log"` became `"/state.log"`, so TicketGen's `EPIC_ID` lookup returned nothing and the phase hard-exited on every run.

  Before escaping a variable, ask which shell owns it: `ticket_slug` is an agent loop variable and must stay escaped; `state_dir` is a function local and must not be. `test-planner-lib-root.sh` guards both directions (Test 7/8 for under-escaping, Test 9 for over-escaping); nothing else will.
- **A dev checkout silently becomes what the plugin runs.** Once `planner-lib-sync.sh` resolves a source checkout, every later session's planner libs come from that working tree — including uncommitted and half-finished edits. That is the point ([#234](https://github.com/willard-pro/claude-plugins/issues/234)), but it means "the installed 0.8.x behaves oddly" can be a local edit rather than a released regression. The hook prints one line naming the checkout whenever it actually copies something, which is the signal to look there first; `PLANNER_DEV_SYNC=0` plus a marketplace re-install restores the released copy.
- **Cross-plugin grill-me dependency:** `planner-intent-gate.sh` resolves `grill-seal.sh` from the grill-me plugin via a three-level fallback (plugin cache → `~/.claude/skills/lib` → relative path). If grill-me is not installed and an intent file is passed, the gate exits 3 with an install instruction. There is no bundled copy — a drifting duplicate would silently pass invalid seals. The gate runs before `planner_state_init` so a rejected intent leaves no state behind.
